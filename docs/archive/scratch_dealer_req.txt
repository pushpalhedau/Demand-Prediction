Dealer Integration Requirements Document
Data, Technical, Security and Onboarding Requirements for Connecting a Dealer / Dealer Group to PredictaX

1. Introduction & Purpose
PredictaX is an AI-powered automobile demand intelligence platform that turns a dealer's historical sales, inventory, and customer data into forward-looking forecasts, stocking recommendations, and customer insight. Value from the platform is directly proportional to the completeness, accuracy, and timeliness of the data it receives from the dealer.
This document defines everything a dealer (or dealer group) needs to prepare, provide, and configure in order to be integrated with PredictaX. It is intended for the dealer's IT, data, and dealership operations stakeholders, and is used jointly with the PredictaX integration team as the basis for onboarding planning, data mapping, and go-live sign-off.
1.1 Objectives of this Document
Define the data the dealer must supply (entities, fields, formats, volumes, and history).
Define the technical prerequisites for connecting to, hosting, or exchanging data with PredictaX.
Define security, privacy, and compliance obligations for handling dealer and customer data.
Define roles, responsibilities, and the onboarding timeline so both parties know who does what, and by when.
Define acceptance criteria used to sign off a dealer as successfully integrated.
1.2 Intended Audience
Dealer / dealer group IT and data management teams
Dealer Management System (DMS) or CRM administrators
Dealership operations and general management sponsors
PredictaX implementation and customer success team
2. Scope
This document covers:
The data entities required for PredictaX forecasting, inventory, and customer-intelligence modules to operate.
The supported data intake methods (file-based bulk load, in-app upload, and direct integration with a dealer's CRM, ERP, or DMS).
File, format, and data-quality standards for every entity.
Infrastructure, environment, and security prerequisites for both PredictaX-hosted and dealer-hosted deployment models.
The end-to-end onboarding process, from kickoff to go-live and ongoing data refresh.
Out of scope for this document:
Internal PredictaX model design, training pipelines, and algorithm internals.
Commercial terms, pricing, and licensing (covered under the separate commercial agreement / SOW).
Market and macroeconomic data (fuel prices, GDP, tariffs, consumer confidence, etc.) — this is sourced and maintained centrally by PredictaX and is not a dealer input.
3. Platform Overview
PredictaX ingests a dealer's transactional and operational data into a relational, star-schema data model, then applies a suite of machine learning models on top of it:
Demand forecasting — Our time-series models projecting unit demand, using macro-economic and seasonal signals as external regressors.
Inventory intelligence — Stockout / overstock risk scoring, reorder point calculation, and 30-day demand forecasts per dealer and vehicle.
Customer segmentation — KMeans clustering into behavioral cohorts (e.g., Budget Buyers, Premium Buyers, EV Enthusiasts, Fleet Buyers).
Lead scoring — A classifier model estimating close probability per lead, with SHAP-based explainability.
Market sentiment — Automated news and sentiment monitoring (independent of dealer data) used as an additional forecasting signal.
Scenario simulation — What-if analysis for macro shocks (fuel price shifts, interest rate changes, EV incentive changes, supply constraints).
All of these outputs are only as good as the dealer data behind them, the remainder of this document defines exactly what that data needs to look like.
3.1 Current Deployment Model
PredictaX is delivered as a single web application backed by a relational database. Data can reach that database either as files exchanged with the dealer (Sections 4.1–4.2) or through a direct connection to the dealer's own CRM, ERP, or DMS (Section 4.3) where that system exposes a usable API, webhook, or database link. Exact connector scope and method are confirmed per dealer during onboarding; a dealer whose systems don't support any direct method can still integrate fully through file exchange.
4. Integration Model
PredictaX supports three complementary data intake paths. Dealers typically use Path A for the initial historical backfill, then either Path B or Path C — or a mix of both — for ongoing refreshes, depending on what their source systems support.
4.1 Path A — Structured Bulk Load (Initial / Historical Data)
The dealer (or PredictaX, on the dealer's behalf) delivers one CSV file per data entity — Dealers, Vehicles, Inventory, Sales, and Customers — matching the exact schema in Section 7. These are loaded into PredictaX's relational database as the authoritative historical dataset used to train forecasting, segmentation, and lead-scoring models. This path is used for the initial go-live load and for periodic full-history refreshes.
4.2 Path B — Dynamic Ingestion Engine (Ongoing Refresh)
PredictaX's in-app “Dynamic Ingestion Engine” (Data Upload & Schema Mapping screen) lets an authorized dealer user upload a CSV directly through the dashboard. The engine auto-detects column types (date / numeric / categorical), runs completeness and shape validation, and — on confirmation — triggers retraining of the customer segmentation and lead-scoring models against the refreshed data. This path is intended for periodic incremental updates (e.g., new sales, updated inventory snapshots) between full bulk loads, and requires the uploaded file's columns to align with the relational schema in Section 7 for the platform to map it correctly.
4.3 Path C — Direct System Integration (CRM / ERP / DMS Connectors)
For dealers who would rather not manage manual file exports, PredictaX can connect directly to the dealer's own CRM, ERP, or Dealer Management System (DMS) instead of receiving CSV files. Depending on what the source system supports, this happens through one of the following:
Native API integration — PredictaX calls the source system's REST/OData API on a scheduled basis (e.g., hourly or daily) to pull new and changed records, authenticated via OAuth 2.0 or an API key issued by the dealer.
Webhook / event push — the source system (or a middleware layer in front of it) pushes new and changed records to a PredictaX ingestion endpoint in near real time as they occur.
Middleware / iPaaS — for source systems without a directly usable API, an integration-platform-as-a-service sits between the dealer's system and PredictaX, handling extraction, transformation, and scheduled delivery.
Direct database connection — for dealers able to expose a secure, read-only reporting replica of their database, PredictaX can connect via a database link (ODBC/JDBC) over a private network or VPN.
In all four cases, the data delivered still has to conform to the entities and fields defined in Section 7 — the connector is simply a different transport mechanism for the same schema, not a different data model.

4.5 Future Capabilities
Two further capabilities are candidates for a follow-on phase, subject to separate technical scoping and not part of the current platform:
Bi-directional write-back — pushing PredictaX outputs (e.g., reorder recommendations, at-risk-lead alerts) back into the dealer's DMS/ERP purchasing workflow or CRM, rather than the dealer acting on them manually inside the dashboard.
Fully managed real-time pipelines — a persistent, monitored connector in place of a scheduled pull, for dealers with very high transaction volume or many integrated locations.

6.2 Data PredictaX Provides (Not a Dealer Input)
The External Factors dataset — fuel prices, GDP growth, inflation, interest rates, consumer confidence, seasonal/holiday flags, tariffs, and regional population/EV-infrastructure data — is sourced and maintained centrally by PredictaX per state/market and used as forecasting regressors. Likewise, news and social sentiment signals are collected and scored automatically by PredictaX. The dealer's only responsibility here is to confirm which state(s)/market(s) their locations operate in, so PredictaX aligns the correct macro data series.
6.3 Minimum Viable Data Set
At minimum, forecasting and inventory features require Sales and Inventory history joined to the Vehicles and Dealers dimensions. Customer segmentation and lead scoring require the Customers entity. A dealer may go live with a reduced field set (see “Required” column in Section 7) and backfill optional fields later — reduced fields will reduce forecast and segmentation accuracy but will not block onboarding.

7.6 Referential Integrity Requirements
Every dealer_id referenced in Sales or Inventory must exist in Dealers.
Every vehicle_id referenced in Sales or Inventory must exist in Vehicles.
Every customer_id referenced in Sales must exist in Customers.
Primary key columns (dealer_id, vehicle_id, sale_id, inventory_id, customer_id) must be unique within their own file.
8. File & Format Standards
8.1 File-Based (CSV) Standards — Paths A & B
File format: UTF-8 encoded CSV, comma-delimited, with a single header row matching the exact field names in Section 7.
One file per entity: dealers.csv, vehicles.csv, sales.csv, inventory.csv, customers.csv.
Dates: ISO 8601 (YYYY-MM-DD). Do not use locale-specific date formats (e.g., DD/MM/YYYY or MM/DD/YYYY).
Booleans: True / False (or 1 / 0, consistently applied within a file).
Currency fields: Plain numeric values in USD, no currency symbols, thousands separators, or parentheses for negatives.
Null / unknown values: Leave the cell empty. Do not use placeholder text such as “N/A”, “NULL”, or “-”.
Identifiers: Stable, unique, and consistent across files and across refreshes (a given dealer_id, vehicle_id, or customer_id must not be reused for a different real-world entity).
File naming: <entity>_<YYYYMMDD>.csv for bulk loads (e.g., sales_20260827.csv), so each delivery is traceable.
Maximum file size (interactive upload): Files uploaded via the Dynamic Ingestion Engine should stay within the per-file limit configured for the dealer's environment (default limit is 200 MB); larger historical extracts should use Path A (bulk load, Section 4.1).
8.2 API / System-Integration Data Standards — Path C
When data is delivered through direct system integration (Section 4.3) rather than as a CSV file, the following standards apply in place of Section 8.1:
Payload format: JSON (preferred) or XML, with source fields mapped to the entity schema in Section 7 during connector setup via a field-mapping workbook completed jointly during onboarding (Section 12).
Incremental sync: each pull or push is scoped by a “modified since” timestamp or change-data-capture marker so only new/changed records transfer, rather than a full re-extract every cycle.
Idempotency: repeated delivery of the same record (e.g., a retried webhook) must not create duplicate rows — records are matched and upserted on their primary key (Section 7).
Pagination & rate limits: API pulls respect the source system's documented page size and rate-limit headers; the connector backs off and retries rather than exceeding published limits.
Time zone: all timestamps are normalized to UTC (or a single agreed time zone) at the point of transfer, to avoid date-boundary mismatches with file-based feeds.
Error handling: failed records are logged with the source system's native identifier and reason, and do not block the rest of the batch from loading.

10. Data Quality, PII, Security & Compliance
10.1 Data Quality Checks Applied on Ingestion
Primary key presence and uniqueness per file.
Referential integrity across dealer_id / vehicle_id / customer_id (Section 7.6).
Required-field completeness (Section 7 “Required” column).
Type/format conformance (dates parse as dates, numerics parse as numbers, booleans are True/False).
Row-count and shape validation against the previous successful load, to catch truncated or partial files.
Duplicate transaction detection on sale_id.
Files that fail validation are rejected with a detailed error report (row/column/reason) returned to the dealer contact for correction and re-submission; the previous good dataset remains active until a corrected file is accepted.
10.2 Personally Identifiable Information (PII)
The Customers entity contains PII (name, demographic data) and sensitive attributes (income, credit score). Before transferring this file, the dealer should:
Confirm a lawful basis / consent exists for using this data for analytics and marketing-response modeling (e.g., email_opt_in must reflect actual, current consent).
Where the receiving environment or contract requires it, pseudonymize direct identifiers (e.g., replace name with customer_id only, and hash any additional identifiers such as email/phone before they are added to the file).
Restrict internal access to the raw file on the dealer's side to authorized personnel only, consistent with the dealer's own data protection policy and applicable regional privacy law.
Notify the PredictaX team of any data subject deletion/erasure requests so the corresponding records can be removed from PredictaX systems.
10.3 Data Transfer & Storage Security
Files must be transferred over an encrypted channel (SFTP, HTTPS upload, or a shared encrypted storage location agreed during onboarding) — plain email attachment of Customers or Sales data is not permitted.
Access to the transfer location and to the PredictaX Dynamic Ingestion Engine must be limited to named, authorized dealer users.
Credentials (transfer-channel logins, dashboard accounts, API keys/environment variables such as DATABASE_URL for a dealer-hosted database) must not be shared over unencrypted channels and must be rotated on personnel change.
A Data Processing Agreement (DPA) / confidentiality addendum covering the data described in Section 7 should be executed prior to the first data transfer, if not already covered by the master services agreement.
10.4 Data Retention & Deletion
Retention periods for dealer data held within PredictaX, and the process for deletion on contract termination or dealer request, should be confirmed in the commercial/data agreement; this document assumes that agreement governs retention and does not itself set a retention period.
10.5 API & Connector Credential Security (Path C)
API keys, OAuth tokens, and database credentials used for direct system integrations are stored encrypted at rest and scoped to the minimum permissions needed — read-only wherever the source system supports it.
Credentials are rotated on a defined schedule and immediately on personnel change or suspected compromise.
Where a third-party middleware/iPaaS platform bridges a source system to PredictaX, that vendor is acting as a data sub-processor and must be disclosed to the dealer and covered under the Data Processing Agreement (Section 10.3).
Connector health and data freshness are monitored so a silent sync failure is caught and alerted on, rather than surfacing later as stale dashboard data.

Separate sandbox/test credentials, distinct from production, should be provided for initial connector build and testing.
The dealer notifies PredictaX in advance of any upgrade, migration, or replacement of a connected CRM/ERP/DMS, since API versions and field structures can change between releases.

13. Testing & Acceptance Criteria
A dealer is considered successfully integrated when all of the following are met:
All five required entity files have been loaded with zero unresolved referential-integrity or required-field errors.
Row counts and key aggregates (total units sold, total revenue, current stock by dealer) in PredictaX dashboards reconcile with the dealer's own source-system reports for a sample period.
Forecasting, inventory-risk, customer-segmentation, and lead-scoring views render without error for the dealer's data.
Named dealer users can log in, view their scoped data, and (where authorized) successfully upload a file via the Dynamic Ingestion Engine.
For dealers integrated via direct system integration (Path C), the connector has completed at least one full, automated sync cycle with zero unresolved errors.
The dealer's business sponsor has reviewed and formally signed off on the initial forecast/segmentation outputs as directionally reasonable.
A data refresh cadence and support escalation path (Section 14) has been agreed and documented.
14. Ongoing Data Refresh, Support & Escalation
14.1 Ongoing Refresh Process
After go-live, the dealer supplies incremental or full-refresh files on the cadence agreed in Section 9, via the same channel used for the historical backfill or via the Dynamic Ingestion Engine. Each refresh should follow the file-naming and format standards in Section 8 so it can be traced and validated consistently.
14.2 Change Management
Any change to the dealer's source-system schema (new fields, renamed values, new vehicle categories, etc.) must be communicated to the PredictaX team in advance of the next refresh.
New dealer locations, discontinued vehicle SKUs, or CRM migrations should be flagged as they occur, not discovered via a failed load.

Appendix B — Glossary
Term
Definition
Bulk Load
A one-time or periodic full-file transfer of an entity's data, loaded directly into PredictaX's database (Section 4.1).
Dynamic Ingestion Engine
The in-app screen allowing an authorized dealer user to upload a CSV and trigger model retraining (Section 4.2).
Direct System Integration (Path C)
Connecting PredictaX directly to a dealer's CRM, ERP, or DMS via API, webhook, middleware, or database link, instead of exchanging CSV files (Section 4.3).
Webhook
An automated, near-real-time notification a source system sends to PredictaX when a record is created or changed.
Middleware / iPaaS
A third-party integration-platform-as-a-service that sits between a dealer's source system and PredictaX, handling extraction, transformation, and delivery when a direct API isn't available.
OAuth 2.0
An industry-standard authorization protocol used to grant PredictaX scoped, revocable access to a dealer's CRM/ERP/DMS API without sharing the underlying account password.
DMS
Dealer Management System — the dealer's core operational system of record for sales, inventory, and service.
Fact Table
A table (Sales) recording individual transactional events, as opposed to descriptive dimension data.
Dimension Table
A table (Dealers, Vehicles, Customers, Inventory) describing an entity referenced by the fact table.
PII
Personally Identifiable Information — data that can identify a specific individual (Section 10.2).
Referential Integrity
The requirement that foreign-key values (e.g., dealer_id in Sales) exist in their parent table (Dealers).
UAT
User Acceptance Testing — dealer-side validation of outputs prior to go-live sign-off.
Star Schema
A data-warehouse design pattern with a central fact table linked to surrounding dimension tables.
